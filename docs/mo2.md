# Цепочка исходники → build → MO2 → игра

## Принцип

Cursor не должен править рабочую сборку. Между кодом и игрой стоит явный шаг сборки:

```
addon/<mod_id>/       редактируем здесь
        ↓ tools/build_addon.py
build/<mod_id>/       артефакт
        ↓ установка/копирование
<MO2>/mods/<mod_id>/  отдельный мод в менеджере
        ↓ галочка в MO2
игра
```

Что это даёт: любой сломанный эксперимент откатывается снятием галочки, а не поиском того, какие файлы Anthology были перезаписаны.

## Раскладка модов в MO2

```
Anomaly 1.5.3 (base)
Anthology 2.1
...аддоны сборки...
My_Fix_Weapon_Jam
My_Fix_Dead_City
My_Addon_Radio
My_Diag_Squad_Spawn      ← диагностика, включается только на время разбора
```

Свои моды всегда ниже сборки: они должны выигрывать конфликт файлов. Диагностические моды держим отдельными строками, чтобы выключать одним кликом.

Каждая версия — своя строка, а не перезапись: `My_Fix_Weapon_Jam` и `My_Fix_Weapon_Jam_v2`. Сравнение «работает/не работает» тогда делается переключением.

## Установка артефакта

Вариант с архивом — через штатный установщик MO2:

```bash
python3 tools/build_addon.py my_fix_weapon_jam --zip
# build/my_fix_weapon_jam-1.0.0.zip → в MO2: Install mod from archive
```

Вариант с прямой установкой в папку модов (быстрее для итераций):

```bash
python3 tools/build_addon.py my_fix_weapon_jam --install "D:/MO2/mods"
```

После этого мод достаточно включить в списке; повторная установка перезаписывает содержимое папки, порядок загрузки сохраняется.

Сверка «что в MO2 устарело относительно `addon/`»:

```bash
python3 tools/check_installed.py "D:/MO2"
```

Скрипт смотрит пакеты с `BUILD_INFO.txt`, сравнивает `built` с mtime файлов в `addon/*/gamedata/`. Моды из SKIP/SEPARATE (`_pack_kristiano_aio`) ставятся отдельно и в «не установлен» не попадают. В CI и при `--no-mtime` сравнение пропускается: после git clone mtime недостоверен (как VERIFY-001).

## Конфликты файлов

Вкладка Conflicts у мода в MO2 показывает, какие его файлы перекрыты и какие он перекрывает сам. Правило разбора: если твой `.ltx` перекрывает файл сборки целиком — это ошибка проектирования, нужен DLTX-патч (`tools/lint_addon.py` это ловит). Патчи `mod_*.ltx` не конфликтуют между собой на уровне файлов, но при override одной и той же секции выигрывает мод, который грузится позже. До установки в MO2: `python3 tools/lint_addon.py --cross` предупреждает (`CROSS-001`), если два мода в `addon/` патчат одну секцию в одном пути внутри gamedata.

## Логи

Перед разбором вылета: скопируй свежий лог в `logs/`, сожми его в карточку и работай по ней.

```bash
python3 tools/xraylog.py logs/xray_<user>.log --out logs/card.md
```

Содержимое `logs/` в git не попадает (кроме `logs/samples/`) — в реальных логах есть локальные пути и имя пользователя Windows.

## Тестовый прогон

Минимальный цикл проверки фикса:

1. Собрать и установить мод.
2. Загрузить сейв, сделанный **до** установки мода, — проверяем совместимость.
3. Воспроизвести сценарий бага.
4. Забрать лог, прогнать через `xraylog.py` даже если вылета не было: `--warnings-only` покажет, не появились ли новые предупреждения.

## Проверка в игре

Агент игру не запускает. Чтобы не терять, какой мод реально проверен, в `meta.ini` необязательные ключи (ставит только человек после сессии):

```
verified_date=2026-08-30
verified_build=Anthology 2.1 / Modded Exes MT 10063
verified_note=что именно проверялось, одной строкой
```

`verified_date` — ISO-дата `YYYY-MM-DD`. `verified_build` — строка сборки **с номером**: `Anthology 2.1 / Modded Exes MT <номер>`. Номер обязателен, его не выдумывают: в логе это `xrCore build 10063`, в карточке `logs/cards/` — поле «Среда». Без номера две проверки на разных билдах не отличить. `tools/lint_addon.py` предупреждает `VERIFY-001`, если ключей нет («в игре не проверялся») или самый свежий файл внутри `gamedata/` новее этой даты («изменён после последней проверки в игре: <дата>»). Правка `meta.ini` / `CHANGELOG.md` / `README.md` дату содержимого не двигает. Закомментированные строки (`; verified_date=...`) не считаются заполненными. `vendor_fork=1` предупреждение не глушит.

Проверка смотрит mtime файлов. Git времена не хранит: после clone все файлы получают время чекаута, и любой `verified_date` выглядит устаревшим. Поэтому `VERIFY-001` имеет смысл только на локальном рабочем дереве. В CI (переменные `CI` / `GITHUB_ACTIONS`) проверка пропускается; явный флаг — `--no-verify`. `--unverified` в таком окружении всё равно печатает список, но предупреждает, что mtime недостоверен.

Рабочий список на сессию в игре:

```bash
python3 tools/lint_addon.py --unverified
```

У форка (`vendor_fork=1`) ключ `vendor_source=<имя папки в reference/addons/>` включает сверку состава: `FORK-001`, если в оригинале есть файл, которого нет в моде. Префиксы `zzz`/`aaa` в имени не считаются пропажей. Файлы, которых нет в оригинале, не ловятся — это наши добавления. Без `vendor_source` проверка пропускается с одной строкой.
