# План: разбор вылета

Для CTD, `FATAL ERROR` и Lua error. Правило: [`.cursor/rules/workflow-crash.mdc`](../../.cursor/rules/workflow-crash.mdc).

Ключевая идея: лог Anomaly — это мегабайты, из которых полезны сотни байт. Если вывалить его целиком в чат, агент утонет в шуме и начнёт угадывать. Поэтому нулевой этап — механическое сжатие лога, а не работа модели.

## Этап 0. Сжать лог

```bash
python3 tools/xraylog.py logs/xray_ivan.log --out logs/card.md
```

Карточка содержит: класс ошибки, блок `FATAL ERROR` целиком, Lua-кадры, последние осмысленные строки перед падением и сгруппированные warning'и. Дальше работаем по карточке.

## Этап 1. Классификация

```
Это разбор вылета, веди по workflow-crash. Этапы 1-3, ничего не исправляй.

@logs/card.md

Что менялось перед вылетом: <новый мод / правка / ничего>
Когда вылетает: <старт игры / загрузка сейва / конкретное действие>
Воспроизводится: <да/нет, как>
```

| Сигнатура в логе | Класс | Первый вопрос |
| --- | --- | --- |
| `CScriptEngine::lua_error`, `...script:NN:` | Lua | какая строка и что там nil |
| `CInifile::r_section`, `Can't open section 'X'` | конфиг | кто ждёт секцию `X` и кто должен был её объявить |
| `Can't find variable X in section Y` | конфиг | какой мод удалил или недоопределил поле |
| `Can't find included file` | конфиг | битый `#include` после установки/удаления мода |
| `D3D`, `CRenderTarget`, `out of memory` | движок | не скрипты: ресурсы, память, шейдеры |
| стек без Lua-кадров, шедулер/потоки | Modded Exes MT | какие MT-тумблеры включены |

## Этап 2. Причина, а не первый кадр

```
Этап 2. Отличи симптом от причины. nil в строке X означает, что объект
не был создан где-то раньше — найди это место. Покажи цепочку:
где значение должно появиться -> где теряется -> где падает.
```

Про MT есть важная поправка: **Lua-машина в Modded Exes остаётся однопоточной**. Многопоточны кости, шедулер, HOM, частицы, загрузка ресурсов; параллельное выполнение `CreateTimeEvent`/`AddUniqueCall` существует, но по умолчанию выключено. Если агент объясняет Lua-крэш «гонкой потоков» — сначала проверь, включён ли соответствующий тумблер, и только потом принимай эту версию.

## Этап 3. Виновник

```
Этап 3. Чей это файл: ванилла, Anthology, сторонний аддон или мой мод?
Если конфликт файлов — какой мод выигрывает по порядку загрузки MO2?
```

Полезная проверка руками: отключить последний установленный мод и повторить. Одна итерация в MO2 дешевле часа гаданий.

## Этап 4. Диагностика, если причина не очевидна

```
Этап 4. Причина не подтверждена. Напиши диагностический скрипт
addon/<mod_id>_diag/, который ТОЛЬКО логирует состояние в точке отказа
через printf с тегом. Игровую логику не менять. Скажи, что я должен
увидеть в логе при каждом из вариантов гипотезы.
```

Диагностика — отдельный мод и отдельный файл, в релиз он не идёт. Требуй заранее сформулированных ожиданий: «если гипотеза A — увидишь X, если B — увидишь Y». Без этого второй лог тоже придётся угадывать.

## Этап 5. Фикс

Только после подтверждённой причины:

```
Этап 5. Минимальный фикс с защитой в точке отказа.
Дальше — этапы 5-6 из workflow-fix.
```

Защита от nil лечит вылет, но не причину. Если непонятно, почему объект оказался nil, в `CHANGELOG.md` это записывается честно: «симптом закрыт, первопричина не найдена».

## Чего не должно быть в ответах

- «Переустанови сборку», «удали gamedata», «проверь целостность» — для MO2-сборки с собственными модами это не диагностика.
- Фикс на этапе 1–3.
- Ссылки на строки лога, которых в карточке нет.
