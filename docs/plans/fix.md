# План: фикс бага

Для случая «механика в сборке работает не так». Правило: [`.cursor/rules/workflow-fix.mdc`](../../.cursor/rules/workflow-fix.mdc).

Ключевая идея: агент почти никогда не ошибается в синтаксисе Lua — он ошибается в том, **что именно** надо чинить. Поэтому первые три этапа не содержат кода вообще, а четвёртый — точка, где ты его останавливаешь.

## Этап 1. Локализация

```
Это фикс, веди по workflow-fix. Этап 1, ничего не редактируй.

Симптом: <что видно в игре, при каких условиях, воспроизводимо ли>
Не проявляется: <когда работает нормально>

Найди в reference/ файл и функцию, отвечающие за это поведение.
Дай пути и номера строк. Если кандидатов несколько — перечисли все
и скажи, какой основной и почему.
```

Признак, что этап провален: агент сразу выдал патч. Тогда — «Ты пропустил этап 1. Верни только список файлов и строк».

## Этап 2. Причина, а не симптом

```
Этап 2. Объясни словами механику: что происходит сейчас, что должно
происходить, в какой строке расходится. Догадки помечай как догадки.
```

Если есть лог, здесь же требуй сопоставления строки лога со строкой кода. Формулировка «скорее всего, где-то не инициализируется объект» — не результат этапа.

## Этап 3. Радиус поражения

```
Этап 3. Найди все места вызова этой функции в reference/ и в addon/.
Отдельно ответь:
- участвует ли значение в сохраняемом состоянии (save_state/load_state);
- переопределяет ли эту функцию какой-нибудь мод сборки;
- есть ли DLTX-патчи на связанные секции.
```

Этот этап чаще всего и отменяет «очевидный» фикс из этапа 2.

## Этап 4. Предложение

```
Этап 4. Сформулируй минимальный фикс в 2-3 предложениях:
способ (DLTX / callback / monkey-patch), список файлов,
и явно — что НЕ меняется. Кода пока не пиши.
```

Здесь принимается главное решение — уровень вмешательства. Порядок предпочтения: DLTX → callback → monkey-patch → замена файла. Если агент предлагает уровень ниже, спроси, почему верхние не подходят.

## Этап 5. Патч

```
Этап 5. Реализуй в addon/<mod_id>/. Оригиналы не заменяем,
сигнатуры не меняем, правка минимальная.
```

## Этап 6. Проверка

```bash
python3 tools/lint_addon.py <mod_id>
python3 tools/lint_addon.py --cross
```

`--cross` без `mod_id` смотрит все моды в `addon/`: фикс может патчить ту же секцию в том же пути, что уже существующий (`CROSS-001`). Один `mod_id` для перекрёстной проверки недостаточен.

```
Этап 6. Проверь:
- места вызова изменённой функции;
- загрузку старого сейва;
- load_state читает оборонительно: исходи из того, что ничего
  не сохранялось (любое поле может отсутствовать);
- фича срабатывает несколько раз подряд;
- поведение в бою, в меню, в торговле;
- где мод должен стоять в порядке загрузки MO2;
- после подтверждения в игре обновить verified_* в meta.ini (только человек);
- запиши CHANGELOG.md.
```

## Что делать, если фикс не сработал в игре

Не «попробуй иначе». Возвращайся на этап 2 с новыми данными:

```
Фикс не сработал. Поведение изменилось так: <что стало>.
Значит, гипотеза из этапа 2 неверна или неполна.
Вернись к этапу 2 и предложи вторую гипотезу, не трогая код.
```

Две неудачные итерации подряд — переходи к диагностическому скрипту из [`crash.md`](crash.md), этап 4. Гадать вслепую дороже, чем один запуск игры с логированием.
